## To skill or not to skill

Skills and plugins are how defined patterns of work accumulate. Every task is a
chance to add to that library, so before starting one, run it through this check.
It is a lens, not a gate: it costs a few seconds and must never delay a task that is
genuinely one-off.

1. **Is it repeatable?** Judge from the shape of the task (would anyone do this
   only once?) and, where available, from history: past sessions, memory, shell
   history, the repo. Lean towards yes.
2. **Can it be automated or assisted, in whole or in part, with tools available
   now?** MCP servers, APIs, a browser, the shell, or written guidance an agent can
   follow. The bar for yes is low: partial automation counts.
3. **Is it already in the library?** Skill discovery should have surfaced it. If
   nothing surfaced, search the skill catalogue or marketplaces before concluding
   it is missing, because an empty lookup is not proof of absence. If it exists,
   use it.
4. **Has someone else already written it?** Look for a third-party or boilerplate
   skill. If it fits as-is, add it to the third-party collection as a pointer to
   its upstream, not a copy. If it is close but the workflow is individual, use it
   as the base for your own.
5. **Otherwise, create it.** Write the skill and add it to the right plugin: public
   if it can be open-sourced, private if it carries personal or business detail.
   Deploy it, then run the task you were about to do as a one-off through the new
   skill. That run is its first validation.

A "no" at step 1 or 2 means: just do the task. Report the verdict in one line
("skill candidate: step 5, new skill `x` in the public plugin") and go on. Creating or
publishing the skill follows the user's standing approval rules. If there are none,
ask once.

Full checklist on demand: skill `skill-or-not:skill-or-not`.
